产品严格遵循六步页面流程：“作品库 → User Idea → Story Concept → Story Blueprint → Chapter Plan → Chapter Workspace → Next Chapter”。UI 交互与信息架构以 prototype/index.html 为唯一权威参考；所有后端实现必须驱动原型中已定义的用户可见状态与交互。AI 永远生成候选内容；只有作者显式确认或应用，候选内容才会改变权威数据。

01 · 范围与关键决策

本期必须交付 MVP Phase 1–6

  • 独立的作品库页面，支持多作品管理、创建与删除。
  • 六步统一导航：作品库、创意、概念、蓝图、章节、工作台。
  • AI 生成设置中心（模型选择、temperature、推理强度），对所有生成入口生效。
  • 逐章激活的顺序写作：Scene → Beat → Prose → Delta → 下一章。
  • State Snapshot / State Delta / 一致性检查 / 后续章节失效标记。

明确不在本期 Phase 3+

  • 账号权限、多作者协同、Redis、向量检索、图数据库与故事分支。
  • 并行生成多个 Scene、自动无确认重写后续正文。
  • 生产 PostgreSQL 与富文本格式；正文权威格式为 Markdown。
v2.0 与 v1.x 的关键差异：① 新增作品库作为入口（多故事管理）；② UI 原型为唯一交互事实来源；③ 统一 AI 生成设置取代分散的模型下拉；④ 章节/Scene 一键生成按钮紧随内容标题；⑤ 创意页在概念生成后自动锁定为只读。
优先级裁决：作者已锁定事实 > 作者已确认内容 > 当前章节已应用内容 > 生成建议 > 未确认计划。

API 层

路由仅验证 DTO、调用应用服务。返回 Pydantic 模型；不泄露 ORM、密钥或完整提示词。

应用服务层

唯一业务入口。负责状态前置校验、事务、乐观锁、审计与跨模块编排。

领域 / 仓储层

领域规则无 HTTP 依赖；仓储只查询和持久化，不编排 AI 或 UI 逻辑。

03 · 领域模型与不变量

Story 1 ── 1 Idea (locked after concept generated) │ ├── 1 Concept (candidate, confirmed) ├── 1 Blueprint (baseline + living state) │ ├── * Entity (Character | Location | Organization | Item | WorldRule) │ ├── * StoryArc │ └── * StateEntry (confirmed only) │ └── * Chapter 1 ── * Scene 1 ── * Beat │ │ ├── 1 StateSnapshot ├── * ProseVersion ├── * ChapterEvent └── * GenerationTask └── * StateDelta

核心不变量

作品库入口 NEW用户从作品库选择或创建故事；未进入故事前，创意/概念/蓝图/章节/工作台 5 个步骤不可见。
创意只读保护 NEWStory Concept 生成后，Idea 页面自动锁定为只读；原始创意不再修改但始终可查看。
Blueprint 双层结构Baseline 保存稳定设定（Characters/World/Timeline/Story Arc）；Living State 投影当前人物/世界/时间线状态。四类 Baseline 确认时创建初始 Living State，后续仅由确认后的 Chapter Delta 更新。
逐章激活首次只激活 Chapter 1；仅当前章完成且 Delta 经作者确认后，才激活 ordinal + 1。
严格顺序生成Scene 和 Beat 均按 ordinal 生成，不可跳过前置项。
Snapshot 无未来信息第 N 章 Snapshot 仅来自 Initial State 与小于 N 的已确认 Delta。
恢复不覆盖恢复历史内容创建新版本，保留版本链与恢复原因。

领域状态

Storyidea → idea_locked → concept_review → concept_confirmed → blueprint_review → blueprint_confirmed → chapter_planning → writing → done
Chapteroutline → locked → active → generating → delta_review → completed；历史变更后 stale
Scene / Beatplanned → available → generating → generated → applied → completed
GenerationTaskqueued → running → succeeded / failed / cancelled；成功不代表已应用
Deltaproposed → checked → confirmed / rejected

05 · 工作流、检查点与失效处理

六步作者流程

作品库创意概念蓝图章节工作台阅读

作品库为入口（多故事管理）；进入故事后显示创意→工作台 5 步；创意页在概念生成后锁定为只读；全书完结（确认最后一章 Delta）后进入阅读模式，已完成作品从作品库直接进入阅读。

章节写作主流程

激活当前章构建 Chapter Context确认 Scene Plan确认 Beat Plan顺序生成正文确认 Chapter Delta更新 Living State激活下一章

两种生成入口，同一执行器

  1. 生成整个章节：从当前第一个未完成 Beat 开始，按 Scene/Beat ordinal 循环到本章结束。
  2. 生成整个 Scene：从该 Scene 第一个未完成 Beat 开始，逐 Beat 生成到该 Scene 结束。
  3. 若已有部分正文，执行器从最后一个已应用 Beat 继续。
  4. 重新生成只允许当前或已生成 Beat；生成后创建新正文版本并触发后续影响分析。

逐级检查点

Beat 完成AI 驱动的 Delta 提取：模型基于本章入口快照从正文提取角色/世界/时间线变化（失败回退确定性规则），并输出一致性发现（与快照矛盾、时间线冲突、已确认事实违背）；确定性规则（过短/占位标记）始终叠加；全部作为 proposed 候选与提醒，不自动覆盖作者事实。
Scene 完成合并 Beat 候选为 Scene Delta；生成 Scene Summary（模型失败回退正文片段），工作台/阅读模式展示，并注入后续场景生成提示保持剧情连贯（修订后续计划）。
Chapter 完成合并 Scene Delta 为 Chapter Delta；作者确认后更新 Story State / Living State 与后序雏形。

Blueprint 更新边界

检查点可自动准备的候选不得自动改变
Beat / Scene 完成人物状态、物品归属、事件、剧情线进度、场景摘要；后续计划修订建议锁定的 Baseline、已确认正文、已确认历史 Delta
Chapter 完成Chapter Delta、Living State 新投影、后序章节雏形修订下一章正文、未来事件的"已发生"状态
作者修改 Baseline影响范围、需重算章节与计划修订建议未经确认直接重写现有章节

06 · AI 适配、上下文与生成设置 UPDATED

模型适配层契约

  • 输入：任务类型、结构化上下文引用、参数快照（来自 AI 生成设置）、令牌预算。
  • 输出：Pydantic 校验的结构化候选；解析失败标 failed。
  • 支持 OpenAI Chat Completions 兼容端点；密钥仅服务端环境读取。
  • 超时、网络错误、无效 JSON 均保留作者草稿，可重试。

统一 AI 生成设置 NEW

  • 作者可随时通过「⚙ 生成设置」配置模型、Temperature、推理强度。
  • 配置跨任务生效，但每次生成时会记录参数快照至 generation_tasks.model_snapshot。
  • 配置入口置于每个有生成操作的页面（创意、概念、蓝图、章节、工作台）。
上下文装配算法规则
1. 确定时间边界当前 Chapter ordinal - 1。
2. 装入目标与 Snapshot目标 Beat/Scene/Chapter 计划 + 本章 State Snapshot。
3. 按预算注入当前计划 → Lock 事实 → 相关实体 → 场景摘要 → 最近正文。
4. 记录引用选中对象的 ID 与 hash，供复现与审计。
5. 禁止装入未来 Delta、未来正文、未确认计划作为事实。

08 · 可靠性、安全与可观测性

必须遵守

  • 所有可变内容版本化；恢复创建新版本，不覆盖历史。
  • 正文与计划使用乐观锁；禁止静默覆盖。
  • 模型密钥仅服务端读取，.env.example 仅放占位符。
  • 日志不记录正文全文、完整 prompt 或密钥；仅 hash、长度、对象 ID、耗时和失败类别。
  • 删除、批量替换、恢复需要确认 API 与审计记录。
  • 生成设置随任务记录为参数快照。

配置与运行边界

  • DATABASE_URL=sqlite:///./novel_ignite.db
  • MODEL_BASE_URL、MODEL_API_KEY、MODEL_NAME 仅后端使用。
  • 本地与测试用 SQLite；测试用 fake adapter，不请求外网。
  • 生产数据库、队列和持久化任务仅在 ADR 批准的后续 Phase 引入。

09 · 工程结构、验收与演进

app/ api/ # routes + Pydantic DTOs infrastructure/ # db, config, model adapter works/ # 作品库 NEW projects/ # story, idea, concept, blueprint lore/ # 全局实体、Lock、版本履历 planning/ # chapters, scenes, beats writing/ # context, generation, prose versions consistency/ # snapshots, deltas, rules, impact main.py prototype/ # UI 权威参考 NEW tests/ migrations/ docs/

最低自动化验收

  • 迁移从空库升级，约束可验证。
  • 创意页在概念生成后不可编辑（409），生成按钮隐藏。
  • Lock 事实不能被生成或普通编辑覆写。
  • 版本冲突返回 409，历史版本仍可读取。
  • 应用正文后创建候选 Delta，不自动确认。
  • 历史变更精确标记后续章节 stale。
  • 模型超时/输出错误不改变作者正文。
  • 原型中定义的所有页面、弹窗、状态均有后端 API 支撑。

Phase 2+ 演进门槛

仅在 MVP 闭环稳定后，按 ADR 引入 PostgreSQL、异步 worker、向量检索或 Story Branch。迁移必须保留对象 ID、版本历史、Snapshot 与 Delta 的可复算性。原型持续同步为交互事实来源。
